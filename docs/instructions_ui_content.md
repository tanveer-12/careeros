# Lumia – UI & Content Generation Instructions

**Document:** `instructions_ui_content.md`  
**Goal:** Define how Lumia generates user‑facing text so it’s **domain‑agnostic**, **no‑hardcoded‑skills**, and **LLM‑only‑on‑demand**.  

This file is for:

- Backend engineers (ranking / plan / FE data‑shape).  
- Frontend engineers (what to render from JSON).  
- Future‑you when you onboard others.  


---

## 1. Design principles

Lumia must work **for any domain**:

- Software engineers, bankers, nurses, researchers, etc.  

Therefore:

- **Never hardcode:**  
  - Exact skills (e.g., “Kubernetes”, “SQL”).  
  - Exact job titles or domains.  
  - Exact programming‑language‑specific phrases.  

- All **core text** must be:
  - **Generated from structured data** (numbers, skill‑lists, fit‑scores).  
  - **Wrapped in neutral‑tone templates** (no tech‑jargon‑biased language).  

LLM‑generated explanations are **optional**, used only when the user explicitly requests them via “AI‑style explanation” / “Show detailed plan” buttons.


---

## 2. Structured data model (no hardcoded text)

All domain‑specific content should live in **data fields**, not in strings.  

### 2.1 `Ranking` object (example shape)

This is the **core data shape** for cluster → resume mapping. Adjust field names to match your ORM.

```python
class Ranking:
    cluster_id: UUID           # role cluster
    cluster_name: str          # e.g., "ML Platform Engineering"
    fit_score: float           # 0–1
    has_skill_count: int       # how many skills user already has
    missing_skill_count: int   # how many skills are missing
    has_skills: List[str]      # list of skills that match the cluster
    missing_skills: List[str]  # list of skills that don’t exist in resume
```

This object is **domain‑agnostic** — it never assumes “software” or “finance”.

## 3. Template‑based summaries (no LLM, domain‑agnostic)

All **default summaries** (shown without user action) must be generated by **pure template functions**, not LLM.

### 3.1 Helper functions (backend)

These functions use **only numeric counts and lists**, no hardcoded skill‑names.

```python
def fit_level(score: float) -> str:
    if score > 0.8:
        return "strong"
    elif score > 0.6:
        return "moderate"
    else:
        return "weak"

def pluralize(x: int) -> str:
    return "skills" if x != 1 else "skill"

def skill_list_str(skills: List[str]) -> str:
    if not skills:
        return "none"
    if len(skills) <= 3:
        return ", ".join(skills)
    return ", ".join(skills[:3]) + " + more"

def generate_skill_summary(ranking: Ranking) -> str:
    fit = fit_level(ranking.fit_score)
    has = ranking.has_skill_count
    missing = ranking.missing_skill_count
    missing_sample = skill_list_str(ranking.missing_skills)
    existing_sample = skill_list_str(ranking.has_skills)

    return (
        f"You are a {fit} fit for this role cluster. "
        f"You already have {has} {pluralize(has)} that match this cluster. "
        f"You're missing {missing} {pluralize(missing)}: {missing_sample}."
    )
```

- `generate_skill_summary(ranking)` is called for **every cluster → resume ranking**.  
- This is the **default UI text** shown in cards, modals, etc.  
- It is **never** generated by an LLM.  

You can add more functions like:

- `generate_cluster_summary(cluster)`  
- `generate_plan_summary(plan)`  

all using the same pattern: **no hardcoded skills / domains**.

## 4. On‑demand AI‑style explanation (LLM‑only)

LLM‑generated explanation is **only triggered when the user explicitly requests it** (e.g., “Show AI‑style explanation”).

### 4.1 Function (backend)

```python
async def generate_ai_explanation(ranking: Ranking) -> str:
    prompt = f"""
    You are a career‑clarity assistant.
    Empathetically explain:
    - Why the user fits this role cluster and what that means for their career.
    - What it means that they are missing certain skills.
    - Keep it short, 3–5 sentences, and domain‑neutral.

    Role cluster: {ranking.cluster_name}
    Fit score: {ranking.fit_score:.2f}
    Missing skills: {', '.join(ranking.missing_skills[:5])}
    Existing skills: {', '.join(ranking.has_skills[:5])}
    """

    # Call your HF‑hosted / HF‑local text‑generation client
    response = await llm_client.achat(prompt)
    return response.strip()
```

- `llm_client` can be:
  - HF Inference API (free‑tier or low‑cost).  
  - Local HF model (e.g., via TGI, Ollama, etc.).  
- **Do not** call this function by default.  
- **Only** when:
  - The user clicks **“Show AI‑style explanation”**, or  
  - The user chooses **“Show detailed plan with AI‑style rationale”**,  

then call `generate_ai_explanation(ranking)` and store it in the DB / return it in the JSON.

## 5. JSON shape (backend → frontend)

When returning data for the UI, use a structure like this:

```json
{
  "ranking": {
    "cluster_id": "uuid",
    "cluster_name": "ML Platform Engineering",
    "fit_score": 0.85,
    "has_skill_count": 8,
    "missing_skill_count": 3,
    "has_skills": ["SQL", "Python", "Airflow", ...],
    "missing_skills": ["Kubernetes", "CI/CD", "dbt"]
  },
  "summary": "You are a strong fit for this role cluster. You already have 8 skills that match this cluster. You're missing 3 skills: Kubernetes, CI/CD, dbt + more.",
  "ai_explanation": null   // or string when requested
}
```

- `summary` is generated by `generate_skill_summary(ranking)`.  
- `ai_explanation` is `null` by default.  
- It is populated **only** after the user requests “AI‑style explanation”.  

This pattern applies similarly to:

- 2‑week‑plan explanations.  
- Cluster‑level descriptions.  
- Any “reasoning” text.  

Always keep the **LLM‑generated** field optional and on‑demand.

## 6. Frontend instructions (UI / UX pattern)

On the web‑app side, the UI should look roughly like this:

```tsx
<div>
  <p className="text-muted-foreground">{ranking.summary}</p>

  {!aiExplanation && (
    <button onClick={fetchAiExplanation}>
      🤔 Show AI‑style explanation
    </button>
  )}

  {aiExplanation && (
    <div className="animate-fade-rise">
      <p className="text-sm text-muted-foreground italic">
        {aiExplanation}
      </p>
    </div>
  )}
</div>
```

- The **default** is the **template‑based summary**.  
- The **LLM‑generated explanation** appears only after:
  - The user clicks the button,  
  - And the FE gets `ai_explanation` from the backend.  

You can add:

- A small **“thinking / generating”** state:
  - “Lumia is analyzing your profile…”  
  - Spinner + fade‑rise into the explanation.  
- This creates the **“Claude‑style thinking” illusion** without using LLM for every sentence.

## 7. How to keep this truly domain‑agnostic

To enforce that **no one hardcodes skills** in strings:

1. **Never** write anything like:
   - `"You need to know Kubernetes and SQL"` in any template.  
   - Skill‑specific domain phrases in UI strings.  

2. **Always**:
   - Put skills / domains inside lists (`has_skills`, `missing_skills`).  
   - Use `skill_list_str(skills)` or `join(skills)` in templates.  
   - Treat **all user‑facing text** as **domain‑neutral** unless it comes from a list or count.  

3. **If you need domain‑specific guidance**, do it via:
   - **Resource‑links** or **learning‑path steps** (e.g., “Learn X from this course”)  
     — but even then, keep the **descriptive text** generic.  
   - Optional:  
     - Let the user **tag** their domain (e.g., “software”, “finance”) and tune only **resource‑links**, not the wording of the text.  

---

## 8. When to deviate from this pattern

You may **break** this pattern only if:

- You are **adding resource‑links** tuned to a domain (e.g., software‑engineering‑specific courses),  
- Or you are working on an **optional, domain‑specific module** (e.g., “Advanced Data‑Science module”) that is **not** the default Lumia behavior.  

Otherwise, **keep everything template‑based, domain‑neutral, and LLM‑optional**.
